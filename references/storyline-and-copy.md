# Executive storyline and copy

Use this reference when planning pages, rewriting titles, simplifying technical language, or resolving a dense proposal.

## Executive reading model

An executive should be able to answer four questions quickly:

1. Why must we change now?
2. What will change in actual work?
3. Why can Eziwork deliver it?
4. What decision is required today?

Build the proposal around those questions. Technical detail supports the decision; it is not the storyline.

## Recommended narrative

Use the following page families when supported by evidence. Merge or split pages to protect readability.

1. Cover and decision-oriented promise
2. Table of contents
3. Current problems expressed as operational and business impact
4. Before-After workflow transformation with measurable proposal targets
5. Eziwork proof: experience → capability → relevance to the client
6. Long-term AX structure and common data connection
7. Why the selected functions are the first priority
8. End-to-end future workflow
9. Current-phase scope versus later expansion
10. What users can actually use at completion
11. Delivery roadmap and approval gates
12. KPI scorecard and decision request
13. Optional closing page

## Title hierarchy

Use compact titles for navigation and a question-form subtitle to tell the reader what each page answers. Place the supported conclusion in the visual or body. This keeps the proposal easy to discuss page by page.

### Cover title

- Preserve the names and capitalization supplied by the user.
- For new proposals, prefer `<Client> <proposal subject> 제안서`; use `AX 개선 제안서` when it describes the actual scope. A user-supplied title takes precedence.
- Place an authorized Eziwork × client logo pair at the upper right, separately from the left-aligned title. The visual pair does not require adding both companies to the written title.
- Remove generic English cover eyebrows such as `SYSTEM IMPROVEMENT`. Preserve meaningful product names and explicit user wording.
- Write the cover subtitle as a question ending in `~할까요?` about the proposed work change. Do not pack the title, scope and promise into one long heading.

### PART title

- Use a short business category that tells the reader where they are in the decision flow.
- Prefer one line and a compact noun phrase.
- Examples: `제안 배경 및 추진 목적`, `현행 시스템 진단`, `통합 시스템 설계안`, `투자 제안 및 의사결정`.

### Page title

- Use a specific noun phrase that names the page's decision topic.
- Prefer one line. Remove introductions such as `~에 대해 설명합니다`, unnecessary subjects, and repeated client names.
- Use the client's operational nouns and familiar product names where they improve clarity.
- Examples: `반복 조회·갱신 현황`, `처리시간 병목 분석`, `n8n 워크플로 재설계`, `운영비 및 총비용 비교`.

### Subsection title

- Use the shortest phrase that distinguishes the subsection from its page.
- Do not repeat the full page title.
- Examples: `데이터 반복 조회`, `상태값 반복 갱신`, `비발송 사전 검증`.

### Question-form subtitle

- Put one natural Korean question directly below every cover and content-page title. End it in `~할까요?` and name the concrete topic the page explains.
- Match the question to the content: current workflow, problem, proposed change, effect, use example or decision. Avoid repeating a generic question on every page.
- Examples: `지금은 계약서가 어떻게 만들어지고 있을까요?`, `어떤 반복 작업이 업무를 길게 만들고 있을까요?`, `채팅으로 진행하면 업무는 어떻게 달라질까요?`, `담당자의 행동은 얼마나 줄어들까요?`, `무엇을 정하면 진행할 수 있을까요?`.
- The visual and body answer the question with evidence-aware statements. A question does not replace the baseline, scope or target-status label.
- A question-only divider already supplies the question; do not add a duplicate subtitle there.

### Sequence check

- Read only the cover, PART, and page titles. They should reveal the proposal's decision path without becoming long sentences.
- A useful default for system-improvement proposals is `배경 → 진단 → 업무 변화 → 설계 → 효과 → 전환 → 책임 → 결정`.
- Adapt the sequence to the evidence and requested decision; do not force empty sections.
- Keep titles concrete and the subtitle question specific; put the supported answer in the visual or body.

Avoid vague titles such as `개요`, `기타`, `AX`, or `시스템 구성` when a more specific title is available. Prefer `핵심 제안 요약`, `AI 생성·검수·승인 연동`, or `통합 시스템 목표 구조`.

## Plain-language replacements

| Avoid when possible | Prefer |
|---|---|
| 데이터 파이프라인 | 데이터가 이어지는 업무 흐름 |
| Human-in-the-loop | 담당자 검토와 최종 승인 |
| 오케스트레이션 | 여러 업무의 연결과 실행 관리 |
| 모듈 | 기능 또는 업무 영역 |
| 퍼포먼스 루프 | 성과 확인과 개선 반복 |
| 데이터 허브 | 공통 데이터 연결 기반 |
| 인게이지먼트 | 반응 또는 참여 |
| 워크플로 | 업무 흐름; 필요할 때만 영문 병기 |
| 누락값 | 빠진 정보 |
| 필수값 검증 | 필수 정보 확인 |
| 화면 진입 | 화면 이동 또는 화면 열기 |
| 요청 해석 | 요청 이해 또는 수정할 내용 확인 |
| 금액·일정은 미확정 | 금액과 일정은 아직 정해지지 않았습니다 |

Use a technical term when it is a required product or system name, then explain it once in plain Korean. Review titles, subtitles, diagram labels, example messages and notes for translation-like wording, awkward particles and compressed fragments. Prefer sentences that describe an action familiar to the client. These replacements apply to reader-facing copy; preserve exact schema fields, identifiers and technical evidence when precision matters.

## Before-After page

Show the current action, the AX-enabled action, the employee's changed role, and the proposal target in one scan path. Avoid a generic two-column list with no process direction.

For each workflow change, state:

`현재 작업 → AX 적용 작업 → 담당자 판단 → 측정 가능한 제안 목표`

Use targets only when the measurement definition and week-one baseline plan are also present.

## Proof and capability pages

- Lead with named organizations only when authorized.
- Connect every experience to a capability and a client application.
- Do not present a logo wall as proof by itself.
- Separate `구축`, `운영`, `추가 개선`, and `교육` experience.
- Mark non-public experience as `Eziwork 제공 정보 기준`.
- If no relevant proof is supplied, omit the proof page or mark the evidence request outside the finished proposal. Do not show empty logo slots or substitute unrelated experience.

## Architecture and scope pages

- Make the long-term total scope and the current implementation scope visually distinct.
- Give each system a one-sentence business function, not only a system name.
- Use color to distinguish current scope, future scope, and shared data foundation.
- Show the data key that connects stages when relevant, such as Content ID or Campaign ID.

## KPI page

Separate productivity, quality, operation, response, and improvement-loop measures when they fit the project. Do not force these categories if the project has a better decision model.

Each KPI must include enough information for the reader to know what success means and how it will be measured.

## Approved Korean reading flow

- Keep title, question-form subtitle and visual about the same concrete problem. A representative should understand the page by reading those three in order; the visual and body answer the question.
- Professional does not mean compressed jargon. Replace fragmentary headings such as `데이터`, `서비스`, `직원이` with distinct business topics such as `데이터 확장성`, `서비스 안정성`, `운영 권한 관리`. Use plain full sentences in the body.
- Use question-only divider pages at major changes of subject when they help: `현재 시스템에는 어떤 문제가 있을까요?`, then numbered diagnostics. Do not add a divider before every page or reinsert a removed one.
- Diagnostics state `현재 상태 → 문제를 만드는 구조 → 운영 영향`. Solutions state `해당 문제 → 개선 방향 → 업무 변화와 효과`. Do not duplicate the entire explanation in both places.
- In solution pages, use the exact problem title as a small eyebrow and a specific large heading such as `콘텐츠 중복 조회 → 워크플로우 최적화`. Keep numbering consistent after merging overlapping problems.
- A repeated-content problem and cloned workflow logic can share one diagnosis page; their time savings and maintenance-count effects may warrant separate solution pages.
- Background: show the customer's concerns as a few professional mid-titles with meaningful icons/charts. If the user removes small prose under those titles, use the visual to explain them rather than adding the prose back.

## Concise, confident, evidence-aware copy

- Prefer affirmative, supported benefits over repeated defensive sentences. `필요한 결과만 전달해 전체 기록 전송을 줄입니다` is clearer than a paragraph ending with `보장하지 않습니다`.
- This preference is not permission to invent certainty, blame the previous developer, hide a meaningful cost exclusion, or call an estimate an observed result. Use short local labels such as `현재 실측`, `개선 추정`, `목표`, `고객 제공·약`, `조건 충족 시` where needed.
- Keep formulas, execution IDs, dates repeated on every page, lengthy verification plans, and meta-commentary out of the main reading path. Preserve their provenance in the evidence register. If a footer is deleted, do not silently convert the associated claim into a guarantee.
- If a small note is clipped or redundant, remove/simplify the requested note and rebalance spacing; do not solve density by shrinking all text. Leave unrelated copy alone.
- Scope and fees are client-specific. Never reuse a previous client's duration, price, installment terms, product selection, or free-plan assumption as a default.

## Risk statements and dispatch improvement wording

- Replace compressed labels with a short full sentence when the user wants the business risk to read more clearly. Examples: `운영 안정성이 위험할 수 있습니다`, `정보 보호·책임 관리가 위험할 수 있습니다`. Explain the concrete cause and consequence below; do not imply an incident has already occurred without evidence. Preserve the user's exact wording when explicitly requested.
- Distinguish a shared login/direct production-DB edit risk from proof that the database product itself is unsafe. Connect the actual access scope to possible critical-data corruption, incorrect dispatch, unnecessary personal-data access and difficult responsibility tracing; then show individual logins, server-side authorization and operator/staff separation as the improvement.
- Avoid doubled wording such as `발송 전송`; use `발송`, `실패 건`, and `자동 재전송`. Without a measured before/after failure rate, use `발송 실패·누락 위험` rather than `실패율 증가`.
- When automatic retry is part of the accepted proposal, a problem-to-effect title can be `발송 실패·누락 위험 → 발송 성공률 개선 및 실패 건 자동 재전송`. A compact alternative is `발송 안정성 개선 및 실패 건 자동 재전송`. The supporting sentence should describe result checking and reduced manual work, not claim a guaranteed percentage.
- Renaming a page also updates navigation and any title index. If the change introduces a new mechanism, align the local flow and explanatory copy with it; do not silently broaden the live system or retrofit unrelated pages. For a title that no longer fits, use an intentional hierarchy/line break rather than shrinking it below readable size.
